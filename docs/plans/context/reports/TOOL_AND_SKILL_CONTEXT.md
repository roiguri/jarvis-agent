# Unload skills before shrinking Jarvis's tools

Every platform surveyed keeps tool and skill context small the same way. A cheap index is always present, full definitions load only on demand, and loading is **append-only**: what has been loaded stays loaded, because changing the tool block mid-conversation invalidates the prompt cache. Anthropic and OpenAI pair this with server-side tool search that adds definitions without touching the cached prefix. Gemini, the model Jarvis runs on, has **no equivalent**. Its implicit cache is prefix-based, and any change to the bound tool set costs cache hits. Jarvis already has the index-plus-on-demand half of the pattern: the whole always-on skill list is about 166 tokens. What it lacks is any way for a loaded skill to leave. On 8–10 skills, accumulated additively on the single `owner` thread since 2026-08-25 and never deactivated, a user call now carries **≈15.5k tokens of tool schemas plus ≈2.9k of skill rules, roughly half of its ≈37k input**. That is about 73 bound tools, against Google's own guidance of "10–20 maximum". On the heartbeat, a `{fitness, google_health}` set frozen since July is ≈38% of every call, and about 38% of those schema tokens belong to tools the heartbeat has never called. The evidence that more tools hurt accuracy is consistent across vendors and three independent papers, but none of it measures Gemini Flash at Jarvis's scale. The cost case is therefore firmer than the accuracy case. The design space comes down to five levers: when skills unload, how the stateless heartbeat picks its tools, whether to trade cache hits for fewer tokens, where rule prose lives, and whether to enforce a schema budget. Each needs an owner decision, and two need a staging measurement first.

## Platforms converge on lazy loading that never unloads

**Anthropic's API** has the most developed mechanism. Tools marked `defer_loading` are still sent in full on every request, but they are kept out of the context window and out of the cached prefix. When the server-side tool search (regex or BM25 variants, up to 10,000 deferred tools) finds one, the API appends a `tool_reference` block inline in the conversation. The docs say "the prefix is untouched, so prompt caching is preserved", and discovered tools remain usable in later turns without another search **[vendor]** ([Tool search tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)). Anthropic advises tool search at "10 or more tools" or "more than 10k tokens" of definitions, and keeping "your 3–5 most frequently used tools non-deferred". It states that selection "degrades once you exceed 30–50 available tools" **[vendor]** (same source). Its caching docs make the stakes explicit. The cache hierarchy is tools → system → messages, and **"Modifying tool definitions → Entire cache"** is invalidated, while changing `tool_choice` invalidates only the messages cache **[vendor]** ([Tool use with prompt caching](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-use-with-prompt-caching)). Agent Skills apply the same three-tier idea to instructions. Metadata of about 100 tokens per skill is always present, the SKILL.md body (under 5k tokens) loads on trigger, and bundled files cost nothing until read **[vendor]** ([Agent Skills overview](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview)).

**Claude Code** turns MCP tool search on by default. Deferred tools appear by name only until `ToolSearch` loads their schemas, and each skill costs one description (capped at 1,536 characters) until invoked. Once invoked, "the rendered SKILL.md content enters the conversation as a single message and stays there across later turns". On compaction, Claude Code re-attaches the most recent invocation of each skill, "keeping the first 5,000 tokens of each" within a combined **25,000-token budget** **[vendor]** ([Claude Code skills docs](https://code.claude.com/docs/en/skills); [Claude Code MCP docs](https://code.claude.com/docs/en/mcp)). There is no unload. Size is managed at compaction time, not per turn.

**OpenAI** offers a soft ceiling of "fewer than 20 functions available at the start of a turn" **[vendor]** ([OpenAI function calling guide](https://developers.openai.com/api/docs/guides/function-calling)). It has two levers. `allowed_tools` restricts which tools are callable while keeping the full list as the cached prefix (same source). From GPT-5.4, Responses API `tool_search` supports deferral and namespaces of "fewer than 10 functions" each, and discovered tools are "loaded at the end of the model's context window… This allows the model's cache to be preserved" **[vendor]** ([OpenAI tool search guide](https://developers.openai.com/api/docs/guides/tools-tool-search)). Codex caps its skill listing at **2% of the context window** (8,000 characters if the window is unknown), shortening descriptions first and then dropping skills with a warning **[vendor]** ([Codex build-skills docs](https://learn.chatgpt.com/docs/build-skills)).

**Google Gemini** advises keeping the "active set to 10-20 tools maximum" **[vendor]** ([Gemini function calling docs](https://ai.google.dev/gemini-api/docs/function-calling)). No tool search or deferral feature was found. Implicit caching is on by default for Gemini 2.5 and newer, with a **4,096-token minimum on 3.x Flash**. It is prefix-based: the docs advise "putting large and common contents at the beginning of your prompt" **[vendor]** ([Gemini caching docs](https://ai.google.dev/gemini-api/docs/caching)). Vertex documents a 90% discount on implicit cache hits for 2.5+ models **[vendor]** ([Vertex context cache overview](https://cloud.google.com/vertex-ai/generative-ai/docs/context-cache/context-cache-overview)). The Developer API rate for 3.x Flash was not confirmed. Explicit caches must contain the tools themselves: a request using `cachedContent` cannot also set `tools`, `tool_config` or `system_instruction` **[vendor, via forum]** ([Google AI developer forum](https://discuss.ai.google.dev/t/structured-output-support-with-cached-content/41525)). Gemini does offer function-calling mode `ANY` with an allowed-names list (the legacy field is `allowed_function_names`). This is the closest analogue to OpenAI's `allowed_tools` (same function-calling docs). Gemini CLI scopes MCP tools only through static `includeTools`/`excludeTools` lists **[vendor]** ([Gemini CLI MCP docs](https://geminicli.com/docs/tools/mcp-server/)).

**OpenClaw and hermes-agent** apply progressive disclosure to skills. OpenClaw renders eligible skills as a compact XML block costing about **24 tokens per skill**, loads bodies through `skills_search`/`skills_read`, and snapshots the eligible list at session start until a refresh trigger **[vendor]** ([OpenClaw skills docs](https://docs.openclaw.ai/tools/skills)). hermes injects an invoked skill as "a fresh user message at invocation time… no system prompt mutation", explicitly to preserve the cache **[vendor]** ([hermes-agent skills docs](https://hermes-agent.nousresearch.com/docs/user-guide/features/skills)). Its cron jobs reportedly attach zero or more skills per job and "run in fresh agent sessions rather than inheriting the current chat" **[community]**, a claim taken from a search summary and not verified on a primary page ([hermes learning path](https://hermes-agent.nousresearch.com/docs/getting-started/learning-path)). Neither platform describes unloading. Disabling a skill is a configuration action.

**Tools-as-code** is the outlier. Cloudflare's Code Mode turns MCP schemas into TypeScript interfaces and runs model-written code in V8 isolates, arguing that "LLMs are better at writing code to call MCP, than at calling MCP directly" **[vendor]** ([Cloudflare blog](https://blog.cloudflare.com/code-mode/)). Anthropic's version reports 150,000 → 2,000 tokens (98.7%) in its example and warns that it needs "sandboxing, resource limits, and monitoring" **[vendor]** ([Anthropic Engineering](https://www.anthropic.com/engineering/code-execution-with-mcp)). These numbers come from catalogs of hundreds of tools. At Jarvis's 78 tools the sandbox costs more than the savings it buys.

Across all of these, **no platform documents per-turn unloading of a loaded tool or skill, and none ships time- or turn-based skill decay**. Where scoping by turn exists, it either restricts *callability* while keeping the definitions (OpenAI `allowed_tools`, Gemini `ANY` plus allowed names) or starts a fresh session per job (hermes cron). The reason is the cache. Once a definition is in the prefix, removing it costs more than keeping it, on every provider that documents its cache rules.

## The evidence on tool count is consistent but mostly vendor-measured

The vendor numbers are large. Anthropic reports that a five-server MCP setup consumed about 77k tokens of definitions, cut to about 8.7k by tool search. Selection accuracy on its internal MCP evals rose **49% → 74% for Opus 4 and 79.5% → 88.1% for Opus 4.5** **[vendor]** ([Anthropic, "Introducing advanced tool use"](https://www.anthropic.com/engineering/advanced-tool-use)). The same post reports that `input_examples` raised complex-parameter accuracy from **72% to 90%**, and that programmatic tool calling cut average tokens by 37%. Anthropic's tool-writing guide adds that "more tools don't always lead to better outcomes" and that "even small refinements to tool descriptions can yield dramatic improvements". It recommends consolidating tools and namespacing them **[vendor]** ([Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)). None of these evals has been independently reproduced.

The independent literature points the same way. **RAG-MCP** retrieved relevant MCP servers before calling the model, cut prompt tokens by over 50%, and raised tool-selection accuracy from **13.62% to 43.13%** **[independent]** ([arXiv 2505.03275](https://arxiv.org/abs/2505.03275)). **"Less is More"** reports up to 70% lower execution time and 35–40% better tool accuracy from dynamic tool selection on edge models. In its most striking case, Llama 3.1-8B fails with the full toolset although it fits in context, and succeeds when given 19 tools **[independent]** ([arXiv 2411.15399](https://arxiv.org/pdf/2411.15399)). Those figures come from summaries of the paper, not its fetched abstract, so treat them as indicative. The most careful recent study, **"How Many Tools Should an LLM Agent See?"** (2026), found that an adaptive shortlist of about **7 tools matched 50-tool coverage** on BFCL (90.3% vs 90.8%). Downstream with Claude Sonnet 4.6, adaptive lists beat fixed 5-tool lists **93.1% to 87.1%** **[independent]** ([arXiv 2605.24660](https://arxiv.org/abs/2605.24660)).

Three limits matter for Jarvis. First, the gains are largest for small models and very large catalogs. Gemini Flash with a few dozen to 73 tools sits in the middle, where a smaller but real effect is the reasonable expectation. Second, **no study separates schema size from tool count**. Jarvis's problem is partly a few very long docstrings rather than many tools, so the literature does not directly price it. Third, there is **no Google accuracy-versus-tool-count data** at all, only the 10–20 guideline. The vendor thresholds are close enough to treat as a band: Google 10–20, OpenAI under 20, Anthropic degrading past 30–50. On caching, the evidence is unambiguous and vendor-documented. Changing tool definitions invalidates cache from that point on, on every provider that publishes its rules.

## Jarvis pays half of every user call for tools it rarely uses

Measurements below come from a read of the staging tree at 8c6cd3f, whose `tools/` and `prompts/` are identical to prod's 3fdd5f7. Usage figures come from prod `turns.jsonl` and `tool_calls.jsonl` for 2026-09-22 → 2026-10-06: 415 turns (314 user, 101 heartbeat) and 1,706 tool calls ([research notes, jarvis_tools](../research_notes/tool-and-skill-context/jarvis_tools.md)). Token counts use the repo's own characters ÷ 4 estimator over the golden snapshots in `tests/golden/tools/` ([tests/golden/surface.md](../../../../tests/golden/surface.md)). Gemini's real token count per `FunctionDeclaration` was not measured, so every share here is an estimate.

**The mechanism works as designed, and its one gap defeats it.** Core tools are always bound. A skill's tools are bound only while its namespace is in the thread's checkpointed `active_skills`, and both the tool list and the system prompt are rebuilt on every LLM call ([tools/registry.py](../../../../tools/registry.py), [agent.py](../../../../agent.py)). The architecture doc states the intent plainly: "A cooking conversation does not carry Sonarr/Radarr/Arbox tool schemas". It defers decay, so skills persist "until explicitly deactivated or the thread is reset" ([docs/architecture/RUNTIME.md](../../../architecture/RUNTIME.md)). There is one `owner` thread for every channel, so "the rest of the conversation" never ends. The only deactivation trigger is a prompt line in AGENTS.md, and the model has called `deactivate_skill` **2 times in the whole log history, against 90 activations**. The owner thread's active set grew from fitness on 08-25 through web, media/radarr, travel, media/system, media/sonarr and github to collections and google_health on 10-04 and 10-05, and **nothing was removed**. It changed in only 4 of 314 user turns. The heartbeat thread has run with exactly `{fitness, google_health}` on 101 of 101 ticks since 2026-07-21.

| Scope | LLM calls | Calls per turn | Input per call | Cache-read per call | Bound tools | Schemas | Skill block | Tool+skill share |
|---|---|---|---|---|---|---|---|---|
| User (current owner set) | 874 | 2.78 | ≈37.0k | ≈17.6k | ≈73 | ≈15.5k | ≈2.9k | **≈50%** |
| Heartbeat | 384 | 3.80 | ≈20.7k | ≈11.6k | 29 | ≈6.8k | ≈1.15k | **≈38%** |

Most of what is bound is never called. Over 14 days, 48 of 78 tools were called at least once. Radarr has 11 tools bound on every user call, and 10 of them were never called (≈920 tokens). Sonarr: 8 of 11 never called (≈780). The whole media family saw **8 calls in two weeks**. Fitness rode on every user call at ≈4k tokens with rules for about 30 calls, and github at ≈1k for 8. Travel is the opposite case. `manage_itinerary` (397 calls) and `manage_place` (283) are the hottest tools in the system, concentrated in 146 turns with up to 26 calls in one turn. On the heartbeat, the six fitness writers and four core tools (`activate_skill`, `deactivate_skill`, `delete_memory`, `get_chat_history`) were never called. That is **≈2.6k tokens, about 38% of the heartbeat's schemas**, sent on all 384 calls.

Size concentrates in a handful of multiplexer tools whose docstrings carry long `Args:` prose. langchain copies the whole docstring into `description`, so descriptions make up **56–78% of schema bytes** per namespace. Six tools account for about 5.5k tokens, more than all 30 media tools combined:

| Tool | Namespace | ≈Tokens |
|---|---|---|
| manage_itinerary | travel | 1,393 |
| manage_collection | collections | 1,015 |
| send_form | core | 654 |
| manage_place / manage_wishlist / manage_trip | travel | 625 / 601 / 592 |
| manage_heartbeat_task | core | 569 |

The core set alone is 11 tools and ≈2.6k tokens in user scope, or 12 tools and ≈2.9k on the heartbeat. RUNTIME.md still describes it as "~9 tools… cost is fixed and cheap". Active skills add their SKILL.md rule bodies to the system prompt: travel 682 tokens, fitness 628, collections 370, google_health 342, web 299, github 254. Several rules are stated **three or four times**. The recurring-versus-one-shot routing rule appears in AGENTS.md, heartbeat.md and both the `manage_heartbeat_task` and `manage_trigger` docstrings. heartbeat.md lines 15–27 are restated almost clause for clause in the `heartbeat_respond` docstring. Travel's wishlist and overnight-arrival rules sit in both SKILL.md and the `manage_itinerary` docstring ([prompts/AGENTS.md](../../../../prompts/AGENTS.md), [prompts/heartbeat.md](../../../../prompts/heartbeat.md), [tools/travel/SKILL.md](../../../../tools/travel/SKILL.md)).

Over the window this comes to roughly **13.5M schema tokens on user calls and 2.6M on heartbeat calls**, plus about 2.9M of skill blocks. That is about 1.4M tokens a day, before discounting the cache-read share. Three caveats apply. First, the brief and the earlier layered-memory report put the heartbeat at ~38.6 KB (≈9.6k tokens) of schemas. The golden-snapshot measurement here gives ≈6.8k tokens of compact JSON. The gap is unexplained (serialization format is the likeliest cause) and only a Gemini `countTokens` reading settles it. Second, about half of per-call input is already cache-read: 48% on user calls and 56% on the heartbeat. Where Gemini places tool declarations relative to the system instruction is **undocumented**, so how much of the schema cost is already discounted is unknown. Third, every tool call in the window has status `ok`. That is execution status, not selection correctness, and nobody has measured whether 73 bound tools cause wrong-tool choices on Flash.

One counter-intuitive finding follows. **Jarvis's sticky activation is accidentally cache-friendly.** The tool block changed in only 4 of 314 user turns, so the prefix stays stable for weeks. Any unloading scheme will churn the prefix more often than today's ratchet does. The question is whether the tokens saved outweigh the cache hits lost. Without knowing where tools sit in Gemini's prefix and what 3.x Flash charges for cached input, that is arithmetic Jarvis cannot yet do.

## Six candidate designs, judged against Gemini's constraints

The layered target architecture fixes the frame. It has a working context with turn-start compaction, an episodic store with one search tool, a capped core, a nightly stateless consolidator, and fresh-context heartbeat ticks that bind "schemas only for the skills the due tasks need". Within that frame, Gemini rules out the mechanism Anthropic and OpenAI rely on. There is no `tool_reference`, so any client-side "load tool" step rewrites the tool block, and the cache benefit those platforms get is unavailable. The candidates below are not mutually exclusive. Most realistic outcomes combine two or three.

**A. Hygiene within today's mechanism.** The first move is to deduplicate prose to one home and add `scopes=("user",)` to the fitness writers, so the heartbeat stops binding them. The second is to consolidate low-use families: 11 radarr and 11 sonarr getters could become a few action-multiplexed tools, as Anthropic's "consolidate tools" advice suggests. The third is to split fitness into read and write sub-skills, a split the triggers plan already needs. The heartbeat saving is ≈2k tokens per call with no change in cache behaviour, because the bound set stays static. This is the lowest-risk option, but it does nothing about the ratchet on the owner thread. Repo history already holds a warning for this lever. A behaviour persisted after its prompt line was removed because a bound docstring's example still advertised it, and "docstring examples can be live bugs" ([docs/plans/context/RESEARCH.md](../RESEARCH.md)). The `input_examples` result (72% → 90%) says examples carry accuracy. Trimming must therefore be behaviour-tested, not just golden-diffed.

**B. Skill decay tied to compaction.** Code deactivates a skill that has not been called for N turns, but applies the change **only when a compaction event rewrites the window anyway**. Compaction already breaks the cache from the history onward, so the extra cost of also changing the tool block is a few kilotokens re-cached once. Of all the options this one most directly attacks the measured ≈5–8k-token per-call surplus on the owner thread, and it fills the decay gap RUNTIME.md deferred. The costs are threefold. A re-activation costs one extra LLM round-trip that re-sends the whole context. The compaction summary must record which skills were recently in use, so the model knows to re-activate. And trimmed history may contain calls to tools that are no longer declared. Anthropic avoids that last problem by never removing definitions. Jarvis would have to confirm on staging how Gemini handles a `functionCall` in history with no matching declaration, or strip such pairs at compaction. `find()` already turns calls to inactive tools into an "activate first" message, so the failure is soft. Decay on an idle timer, without the compaction tie, is the simpler variant and churns the cache at unpredictable times.

**C. Stable superset, restricted callability.** Bind a fixed superset and narrow what can be called per turn with Gemini's mode `ANY` plus allowed function names. This mirrors OpenAI's `allowed_tools`. It keeps the cache and might help selection accuracy, but **saves no tokens**, and `ANY` forces a function call on every step. That clashes with Jarvis turns that end in plain text. Whether langchain-google-genai exposes the newer `tool_choice` shape or only the legacy field needs checking. It is a poor fit for the measured problem, which is cost.

**D. Per-task scoping for the stateless heartbeat.** Each fresh tick binds core plus the skills its due tasks declare, for example a `skills:` field on a HEARTBEAT.md task header, much as hermes reportedly attaches skills per cron job. The set is fixed at tick start and stays fixed for the tick's ~3.8 calls, so the within-tick cache holds. Across ticks the prefix varies with the due set, but ticks are an hour apart, so cross-tick cache reuse is small anyway. A tick whose due tasks need no skill would bind core alone (≈2.9k tokens), and a fitness tick would bind fitness-read only. This option falls out of decision 1 of the layered architecture almost for free, and it removes the frozen July activation set. The open sub-question is whether a tick may still `activate_skill` mid-tick for unanticipated work, or whether the task declaration is the only door.

**E. Router-selected tools per user turn.** A cheap pre-call step (embedding match or a Flash classifier) picks skills for each user message. This is RAG-MCP and the adaptive-shortlist paper applied at skill granularity. It gives the biggest token saving and the strongest evidence for accuracy, at the cost of a different prefix on many turns and a misroute failure mode where the needed tool is simply absent. At 12 skill namespaces with a 166-token index the model already reads, a router mostly duplicates what `activate_skill` does. It earns its place only if B proves insufficient.

**F. Tools as code or emulated tool search.** Rejected at this scale. Code Mode needs a sandbox. Emulating `defer_loading` on Gemini means a meta-tool that rewrites the tool block, which gives all of B's cache cost with none of its batching. Jarvis's skill index is already a namespace-level tool search.

| Option | Token effect | Gemini cache effect | Accuracy evidence | Main risk |
|---|---|---|---|---|
| A. Hygiene and scopes | −2k heartbeat; −hundreds user | Neutral | Description quality matters [vendor] | Docstring edits change behaviour |
| B. Decay at compaction | −5–8k user | One re-cache per compaction | Fewer tools helps [vendor + independent] | Re-activation round-trips; orphaned calls |
| C. Superset + allowed names | None | Preserved | Plausible, unmeasured | `ANY` forces calls |
| D. Per-task heartbeat scoping | −2–4k heartbeat | Within-tick preserved | Fewer tools helps | Under-declared tasks |
| E. Per-turn router | Largest | Frequent prefix churn | Strongest [independent] | Misroutes remove the needed tool |
| F. Code / emulated search | Large at big scale | Worst on Gemini | Vendor only | Sandbox; complexity |

## Decisions the owner must make

**Decision 1: does a loaded skill ever leave the owner thread?** The choices are three: keep today's sticky behaviour and accept ≈50% of each user call; add decay, either on an idle timer or tied to compaction (B); or route per turn (E). B fits the layered architecture best, because compaction becomes the single moment when the working context, and now the tool surface, is rebuilt. Its sub-decisions are the idle threshold, whether travel-scale skills get a longer one, and whether the compaction summary lists recently used skills. Whichever option is chosen, RUNTIME.md's deferral note and the AGENTS.md "deactivate when no longer needed" line should change with it. The prompt line has demonstrably not worked (2 deactivations in three months).

**Decision 2: how does a stateless tick choose its tools?** The options are task-declared skills (D), model activation inside each fresh tick, or a code-defined "heartbeat core" that replaces the frozen `{fitness, google_health}`. Task declaration gives code the decision, matches the "code decides when the model runs" philosophy of the gate, and is the cheapest to test, because `turns.jsonl` can log the due set and bound set per tick. That also closes the earlier report's gap that per-task heartbeat cost is unmeasurable. Whether writers should ever be bound on ticks follows from the layered report's rule that ticks are "read-only except through notify, triggers and confirmation".

**Decision 3: tokens or cache hits, and measure before choosing.** Decisions 1 and 2 both trade prefix stability for fewer tokens, and the exchange rate is unknown. Three readings would settle it: Gemini `countTokens` on the actual declarations Jarvis binds, the cached-token share per call before and after a forced tool-set change on staging, and the Developer API cached-input rate for the 3.x Flash model in use. This overlaps the open caching item (B2) from the context work. If the tool block turns out to sit before the system instruction and to be almost fully cached, the cost case for B weakens to the accuracy case alone. If it sits after the per-turn system content, the case gets stronger.

**Decision 4: one home for each rule.** The repo's established finding is that docstrings, not prompt prose, drive behaviour. That argues for making the docstring the single home for anything tied to a tool's use. SKILL.md bodies would shrink to cross-tool workflow, and AGENTS.md and heartbeat.md would keep only rules not tied to any one tool. Moving prose between a docstring and a SKILL.md body saves nothing on its own, because both are present exactly when the skill is active. The saving comes only from removing duplicates. The heartbeat_respond restatement and the four-way routing rule are the first candidates. The sub-decision is whether long worked examples stay. The vendor evidence (72% → 90% from examples) and the repo's own experience of examples acting as live instructions both say examples are behaviour, not overhead.

**Decision 5: a schema budget enforced in CI.** `tests/golden/surface.md` already prints per-namespace token cost on every docstring change. A ceiling per namespace, and one for core, would make the "slash command over skill over core tool" rule, which already rejected an always-on `manage_timezone`, mechanical rather than remembered. This is the tool-side analogue of the harness-enforced file caps proposed for L1. The layered architecture also changes core itself. One episodic search tool would replace `get_chat_history` and `get_notification_history` (≈230 tokens), and any added tool should be charged against the same budget.

**Decision 6: restructure the outliers or leave them.** Media's 22 radarr and sonarr getters (2 kilotokens for 8 calls in two weeks) and the fitness read/write split are cheap consolidations whatever happens with decay. Travel's `manage_itinerary` (1.4k tokens, 22 arguments in prose) is the hardest case, because it is also the most-used tool. Shortening it risks the behaviour that makes it work. Shortening only makes sense if decay alone does not bring user calls back under a target the owner sets.

Several things remain unknown. No source documents where Gemini serializes tools in its cache prefix. No evidence covers Flash's selection accuracy at 29 or 73 tools. Jarvis does not log the target of `activate_skill` or the bound tool list per call, so the activation timeline above is inferred from `active_skills` diffs. Two pieces of logging would turn the next reading from inference into observation: the bound-tool list per call in telemetry, and the due-task set per tick.

## Conclusion

The research shifts the question from "how do we shrink tool schemas" to "when is Jarvis allowed to change them". Every platform that documents its caching treats a tool-set change as expensive, and none unloads per turn. So Jarvis's never-deactivate behaviour is not a bug relative to industry practice. It is what Claude Code and OpenClaw do too. The difference is that they run over sessions that end, while Jarvis runs a single thread that has lasted six weeks and still grows. The right unload moment is therefore one where the prefix is being rebuilt anyway: a compaction event on the owner thread, and the start of every tick once the heartbeat is stateless. That ties the tools question to two decisions the layered-memory redesign already has to make. It does not open a separate workstream.

The second takeaway concerns evidence. The industry's most dramatic accuracy and token figures come from catalogs of hundreds of tools on Claude and GPT, which tells Jarvis little about 73 tools on Gemini Flash. The cheapest high-value step is not a design at all. It is three staging readings (real token counts, the cache share across a tool-set change, and the cached-input price) plus two log fields. Without them any option here is priced by guesswork. With them, decay at compaction and per-task heartbeat scoping can be judged on Jarvis's own numbers, as the context work's before/after discipline already requires.
